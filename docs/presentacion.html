La aplicación

Registras tus evaluaciones (nombre, peso en % y nota de 0 a 5) y calcula cuánto necesitas en lo que falta para llegar a 3.0.

EvaluaciónPesoNotaAporte
Parcial 130 %3.51.05
Parcial 230 %——
Taller20 %4.50.90

Las reglas

La nota va de 0 a 5 y se aprueba con 3.0.

Los pesos suman 100 % como máximo.

No hay dos evaluaciones con el mismo nombre.

Estados: aprobado, en camino, en riesgo, imposible.

El problema de hoy

Todo vive en una pestaña de un navegador.

Queremos las mismas notas en el celular y el portátil, un solo dueño de las reglas y que otras aplicaciones las consulten.

Hoy no cambiamos la aplicación: le ponemos un servidor y una API.

Primer concepto

¿Qué es una API?

Un contrato: qué se puede pedir, con qué forma y qué se recibe a cambio. Quien la usa no ve lo que hay dentro.

API en el mismo programa

Llamas un método.

Mismo lenguaje, misma máquina.

No falla por culpa de una red.

API web

Mandas una solicitud HTTP.

Otra máquina, quizá otro lenguaje.

Tarda, falla y puede cambiar sin avisarte.

El Modelo de la clase pasada ya era una API: agregar, calificar, eliminar, resumen. Hoy esa API cruza una red.

Arquitectura de Software · Tema 2.4 · Diseño de APIs

La tentación

Guardar todo, cada vez

La API más fácil de escribir

PUT /guardarTodo

[ { "id": 1, "nombre": "Parcial 1", … },

  { "id": 2, "nombre": "Taller", … } ]

Así se pierde una nota

portátil  lee la lista .......... [Parcial, Taller]

celular   lee la lista .......... [Parcial, Taller]

portátil  califica y guarda ..... Taller = 5

celular   guarda SU lista ....... Taller = —  (pisa)

Se pisan

Dos aparatos guardan su propia lista: gana el último y el otro pierde su trabajo sin enterarse.

Las reglas se escapan

Quien use curl se salta cualquier validación del navegador: el servidor guarda lo que le manden.

No hay recursos

Un solo cajón: no se puede leer, cambiar o borrar una evaluación, ni darle una dirección.

Es lo más fácil de programar y lo primero que se rompe. Lo van a criticar en el laboratorio.

Arquitectura de Software · Tema 2.4 · Diseño de APIs

REST

Un estilo de arquitectura, no un protocolo

Roy Fielding, tesis doctoral, 2000. REST no es «JSON sobre HTTP»: es un conjunto de restricciones que, juntas, dan una API que escala y evoluciona.

Cliente–servidor

El navegador y el servidor cambian por separado; solo comparten el contrato.

Sin estado

Cada solicitud trae todo lo necesario. El servidor no recuerda «la sesión».

Caché

Las respuestas dicen si se pueden reutilizar (ETag, 304 Not Modified).

Interfaz uniforme

Recursos con dirección, métodos con significado y mensajes que se explican solos.

Por capas

El cliente no sabe si habla con el servidor o con un proxy o un balanceador.

Código bajo demanda

Opcional: el servidor puede enviar código al cliente (como el JavaScript de la página).

Arquitectura de Software · Tema 2.4 · Fielding (2000), capítulo 5

Primera decisión de diseño

Recursos, no acciones

/v1/evaluaciones

La colección: se lista y se agrega.

/v1/evaluaciones/{id}

Un elemento: se lee, se modifica y se borra.

/v1/resumen

Un recurso calculado: no es una fila de datos, pero tiene dirección.

Una representación

GET /v1/evaluaciones/1

 

{ "id": 1,

  "nombre": "Parcial 1",

  "peso": 30,

  "nota": 4 }

El recurso es el concepto; la representación es una foto de su estado, en un formato. No es el objeto interno del Modelo: es un contrato.

La dirección nombra. El método actúa.

Lo que responde el servidor

Códigos de estado que sí vas a usar

EstadoQué dice
200 OKSalió bien; hay cuerpo.
201 CreatedSe creó algo; Location dice dónde vive.
204 No ContentSalió bien; no hay nada que devolver.
304 Not ModifiedNo cambió desde la versión que ya tienes.
400 Bad RequestNo se entiende la solicitud.
404 Not FoundEse recurso no existe.
405 Method Not AllowedEse método no va en esa dirección; Allow dice cuáles sí.
409 ConflictChoca con el estado actual de los datos.
415 Unsupported Media TypeEl formato del cuerpo no es el esperado.
422 Unprocessable ContentSe entiende, pero un valor incumple una regla.
500 Internal Server ErrorFalló el servidor; nunca con trazas ni detalles internos.

2xx salió bien · 3xx ya lo tienes · 4xx el cliente se equivocó · 5xx falló el servidor

Arquitectura de Software · Tema 2.4 · nombres según RFC 9110

Votación · 4 minutos

¿Qué estado devuelve?

  1. Mandan un JSON al que le falta cerrar una llave
  2. Piden GET /v1/usuarios/999 y no existe
  3. Registran un correo que ya tiene una cuenta
  4. Escriben el correo «ana@@casa» (formato inválido)
  5. Mandan el cuerpo como text/plain a un endpoint que solo lee JSON
  6. Piden DELETE /v1/usuarios (la colección entera) y esa operación no existe
  7. Ponen la edad −5 en una solicitud que el servidor entiende

Voten para cada una: 400 · 404 · 405 · 409 · 415 · 422

Una respuesta bien hecha

Éxito y error, los dos con forma

Éxito · 201 Created

POST /v1/evaluaciones

{ "nombre": "Final", "peso": 30 }

 

201 Created

Content-Type: application/json

 

{ "id": 3, "nombre": "Final",

  "peso": 30, "nota": null }

Error · application/problem+json

GET /v1/evaluaciones/99

 

404 Not Found

Content-Type: application/problem+json

 

{ "type": "…/problemas/no-existe",

  "title": "La evaluación no existe",

  "status": 404,

  "detail": "No existe la evaluación.",

  "instance": "/v1/evaluaciones/99" }

type qué problema es (identificador estable) · title resumen, igual siempre · status el estado · detail este caso, para personas · instance qué solicitud lo causó

Arquitectura de Software · Tema 2.4 · RFC 9457: Problem Details for HTTP APIs

Colecciones grandes

Listas: paginar, filtrar, ordenar

Una página de la lista

GET /v2/evaluaciones?estado=pendiente

      &orden=-peso&porPagina=2&pagina=2

 

200 OK

Link: </v2/evaluaciones?…&pagina=1>; rel="prev",

      </v2/evaluaciones?…&pagina=3>; rel="next"

 

{ "datos": [ … ],

  "paginacion": { "pagina": 2, "porPagina": 2,

                  "total": 5, "totalPaginas": 3 } }

Paginar

Nunca devuelvas una lista sin tope: con diez mil filas sufren el servidor y el cliente.

Filtrar y ordenar

Van en la consulta, no en la ruta. Un valor inválido es un 400.

Navegar

La respuesta dice dónde está lo siguiente: cabecera Link (RFC 8288).

Y un arreglo pelado no tiene dónde decir «total». Eso va a importar enseguida.

Cambiar sin romper

Una API publicada es una promesa

No rompe a nadie

Agregar un campo opcional a una respuesta

Agregar un endpoint nuevo

Aceptar un valor más en una entrada

Hacer opcional lo que era obligatorio

Rompe a los clientes

Quitar o renombrar un campo

Cambiar su tipo («4.2» en vez de 4.2)

Cambiar la forma: de arreglo a objeto

Exigir un campo nuevo en la entrada

Cambiar el significado de un valor

La lista de la v1 es un arreglo. Paginarla la volvería un objeto: eso rompe. Hace falta una versión nueva.

Dónde va la versión

Cuatro maneras de versionar

EstrategiaEjemploA favorEn contra
En la direcciónGET /v2/evaluacionesSe ve, se prueba en el navegador y con curl, se enruta fácilLa misma «cosa» tiene dos direcciones
Cabecera propiaApi-Version: 2La dirección no cambiaInvisible: no se prueba pegando un enlace
Tipo de medioAccept: application/vnd.notas.v2+jsonVersiona la representación, no el recursoMás difícil de usar, documentar y cachear
ParámetroGET /evaluaciones?version=2Fácil de agregarSe mezcla con los filtros; es fácil olvidarlo

En el laboratorio: la dirección. No es la única respuesta correcta; sí la más fácil de ver y de probar.

El ciclo de vida de una versión

Vigente

hasta hoy

Obsoleta

Existe la v2; la v1 avisa.

desde el 1 oct 2026

En retiro

hasta el 31 dic 2027

Retirada

Responde 410 Gone o 404.

después

Lo que dice la v1 en cada respuesta

Deprecation: @1790812800                        # obsoleta desde el 1 de octubre de 2026

Sunset: Fri, 31 Dec 2027 23:59:59 GMT           # se retira el 31 de diciembre de 2027

Link: </v2/evaluaciones>; rel="successor-version"   # y la nueva está aquí
