Laboratorio: una API REST para las Notas

Reciben la aplicación MVC de la clase pasada, cuyo Modelo vivía en el navegador, y le ponen un servidor con una API REST: diseñan los endpoints, escogen los códigos de estado, versionan sin romper a nadie y la documentan con OpenAPI. Trabajan en equipo, con JavaScript puro: sin frameworks y sin instalar dependencias. Unas pruebas les dicen si lo hicieron bien.

Qué van a lograr

  • Diseñar endpoints como lo hace una API REST: recursos como sustantivos, métodos HTTP con su significado, códigos de estado correctos y errores que una máquina y una persona puedan leer.
  • Llevar un Modelo MVC al servidor y conectar el navegador con una API sin tocar la Vista: ver qué cambia y qué se queda quieto.
  • Decidir dónde viven las reglas de negocio (el servidor es el único dueño) y qué se traduce en la frontera entre el negocio y HTTP.
  • Versionar sin romper: lanzar una v2, mantener la v1 y avisar que se retira con las cabeceras estándar Deprecation y Sunset.
  • Documentar la API con OpenAPI y comprobar con pruebas que la documentación no se contradice con el código.

Reglas del laboratorio

1. El Modelo no sabe de HTTP: ni estados, ni rutas, ni fetch. 2. Las rutas traducen, no deciden: no llevan reglas de negocio. 3. La URI nombra recursos (sustantivos) y el método HTTP es la acción: nada de verbos en la dirección. 4. El navegador no tiene reglas y solo cliente-api.js habla HTTP. 5. La v1 no se rompe: lo nuevo va en la v2.

Antes de la clase

No hay descargas pesadas: todo cabe en unos pocos archivos. Aun así, comprueben su equipo con calma el día anterior.

  • Node.js 18.2 o superior (recomendado 20 o 22). Comprueben con node -v. Si no lo tienen, instalen la versión LTS desde nodejs.org. ¿No pueden instalar nada? Hay un Plan B al final de esta guía.
  • Git. Comprueben con git --version.
  • Visual Studio Code (recomendado) y un navegador moderno con herramientas de desarrollo (Chrome, Edge o Firefox).
  • Una cuenta de GitHub por integrante. Una persona del equipo crea el repositorio y agrega al resto como colaboradores.
  • Haber hecho (o al menos recordar) el laboratorio de MVC. No necesitan su código: esta plantilla trae la aplicación de la clase pasada ya terminada.
  • Equipos de 2 o 3 personas. En pareja trabajen como conductor y navegante y cambien de rol en cada parte.

Los cuatro cambios del Modelo

Es el mismo Modelo de la clase pasada, con tres cosas que un API necesita y una que mejora un detalle: (1) cada ErrorDeReglas trae un codigo estable (el mensaje sirve para personas; el código, para máquinas); (2) agregar y calificar devuelven la evaluación (hay que responder con ella); (3) existe obtener(id); (4) calificar comprueba primero que la evaluación exista (un recurso que no existe es un 404 aunque el cuerpo también tenga errores).

Parte 1 · Diseñar el contrato

20 min

En la clase pasada el Modelo era un objeto con métodos. Para que el navegador y el servidor se hablen, cada operación debe volverse una solicitud HTTP. Antes de escribir una línea, diseñen ese contrato en papel: es la parte más barata de equivocarse. Esta parte no escribe código.

Siete reglas para diseñar endpoints

1. La URI nombra un recurso (sustantivo); el método HTTP es la acción.  2. Las colecciones van en plural y un elemento cuelga de su colección: /evaluaciones/{id}.  3. Minúsculas, guiones si hay varias palabras, sin extensión (.json) ni barra final.  4. La versión va en la URI: /v1/….  5. Lo que filtra, ordena o pagina va en la consulta (?estado=pendiente&pagina=2), no en la ruta.  6. El éxito o el fracaso lo dice el estado HTTP, nunca un campo ok en el cuerpo.  7. Todos los errores usan el mismo formato legible (application/problem+json).

Método¿Seguro?¿Idempotente?Se usa para…
GETSí: no cambia nadaSíLeer un recurso o una colección
POSTNoNoCrear (el servidor decide la dirección del recurso nuevo)
PUTNoSíReemplazar un recurso completo
PATCHNoNo por definición (depende de la operación)Cambiar una parte de un recurso
DELETENoSíBorrar un recurso

Idempotente quiere decir que repetir la misma solicitud deja el servidor en el mismo estado que hacerla una vez. No habla de que la respuesta sea idéntica.

  1. Hagan la crítica de ENTREGA.md, sección 1b: seis direcciones mal diseñadas. Para cada una escriban qué regla rompe y cómo la reescribirían.
  2. Comparen con otro equipo durante 3 minutos: ¿coinciden en las URI y los métodos? ¿Dónde discreparon y por qué? Todavía no miren las pruebas: primero su propio criterio.

Listo cuando: la tabla de la sección 1 está completa y pueden explicar por qué ninguna URI lleva un verbo. No hay commit todavía: el contrato se confirma con el código en la Parte 2.

Parte 2 · El servidor: la API v1

35 minControlador de la API

Abran servidor/rutas.mjs. Los manejadores son el Controlador del servidor: traducen una solicitud HTTP en una orden para el Modelo y el resultado (o el error) en una respuesta HTTP. Ya viene resuelto un ejemplo, resumen: léanlo primero. Las pruebas de pruebas/api.pruebas.js son la especificación.

Qué recibe y qué devuelve un manejador

Recibe una solicitudDevuelve una respuesta
params → { id: "3" } (siempre texto) · query → ?pagina=2 como query.get('pagina') · cuerpo → el JSON ya leído y validado (solo en POST/PATCH) · base → "/v1" · ruta · cabeceras { status, cuerpo?, cabeceras? }: el estado, el JSON a enviar y las cabeceras extra. Para fallar: throw new ErrorHttp(estado, 'detalle para humanos'); los errores del Modelo los traduce traducirError, la tabla que van a escribir.

Nunca tocan req ni res de Node: de eso se ocupa el núcleo. Tampoco validan nada que el Modelo ya valida: si se descubren escribiendo if (peso > 100) en una ruta, deténganse.

Paso a paso

  1. 2A · Leer (≈ 10 min). Implementen listarV1 y obtener y regístrenlos en la tabla de rutas junto con el resumen (recuerden: la URI de una evaluación lleva {id}). El Modelo ya sabe devolver la lista y una evaluación; usen representarEvaluacion para no filtrar nada interno. Prueben a mano: curl -i localhost:3000/v1/evaluaciones (¿qué estado y qué Content-Type ven?) Si quieren ver filas antes de poder crearlas (eso es 2B), creen el archivo datos/notas.json con [{"id":1,"nombre":"Parcial 1","peso":30,"nota":4}] y reinicien el servidor. Ejecuten npm run test:api: el grupo 2A debe quedar completo. La app del navegador ya debería dibujar la lista (todavía no puede crear).
  2. 2B · Crear y la tabla de estados (≈ 12 min). Primero, ESTADO_POR_CODIGO y traducirError: cada error del Modelo trae un codigo y ustedes deciden el estado HTTP (la tabla de abajo ayuda). Después, crear: debe usar solo nombre, peso y nota del cuerpo (el id lo decide el servidor), responder con el estado correcto para «creado», con la cabecera Location apuntando a la evaluación nueva y con su representación. Regístrenlo. Grupo 2B en verde.
  3. 2C · Modificar y borrar (≈ 8 min). calificar cambia solo la nota (el cuerpo es { "nota": 4.5 }, o null para quitarla) y devuelve la evaluación actualizada; eliminar responde sin cuerpo. Regístrenlos. Grupo 2C en verde. Con la app abierta ya pueden agregar, calificar y eliminar.

Los errores del Modelo: ¿qué estado le corresponde a cada uno?

Tres grupos de situaciones: el recurso no existe; el contenido enviado incumple una regla (un valor inválido) y el contenido choca con el estado actual del sistema (algo ya existe, un tope se agotó). Los estados candidatos son 400, 404, 409 y 422. Decidan y justifiquen en ENTREGA.md (sección 2).

NOMBRE_LARGOEl nombre pasa de 40 caracteresEl nombre no puede superar 40 caracteres.
PESO_FUERA_DE_RANGOEl peso no es un número entre 1 y 100El peso debe estar entre 1 y 100.

Una cosa a la vez

npm test muestra un grupo a la vez, con esperado contra recibido. Con npm test -- --todo ven todos los fallos y con npm run test:api solo los de esta parte. Si cambiaron un archivo y no ven efecto en el navegador o en curl, reinicien el servidor (con npm run dev se reinicia solo).

400, 404, 405, 409, 415, 422… ¿cuál?

No hay una respuesta única en la industria: hay convenciones. Las de este curso: 400 si la solicitud no se puede entender (JSON roto, no es un objeto, un parámetro de la dirección inválido); 415 si el formato no es JSON; 422 si se entiende pero un valor incumple una regla; 409 si choca con el estado actual; 404 si el recurso no existe; 405 si el método no existe en esa dirección. En un proyecto real documentan su convención; lo grave es cambiarla a mitad de camino.

Listo cuando: npm run test:api muestra los cuatro grupos en verde y el grupo Las rutas son el Controlador de la API de npm run arquitectura también. Commit: Parte 2: API v1.

Parte 4 · Versionar: la v2

25 min

Hay un problema de diseño: GET /v1/evaluaciones devuelve un arreglo pelado, y un arreglo no tiene dónde decir «hay 73 en total, esta es la página 2». Cambiarlo a un objeto rompería a todos los clientes que ya existen (incluido el compañero que ya usa su API). La solución: una versión nueva, la v2, con la forma nueva, y la v1 intacta pero con avisos de que va a retirarse.

  1. 4A · La lista de la v2 (≈ 12 min). Implementen listarV2 en rutas.mjs. El comentario trae los pasos. El contrato:

Todo lo que no cambió (crear, obtener, calificar, eliminar, resumen) debe funcionar igual en /v2/…, sin copiar y pegar: agrupen esas entradas con paraVersiones(['v1', 'v2'], [...]) (sin el prefijo /v1 en las rutas) y registren aparte las dos listas. Cuidado: Location de un POST a /v2/… debe apuntar dentro de /v2/ (hay un dato en la solicitud, base, que ayuda). Grupo 4C en verde.
  4. 4D · Migrar el cliente (≈ 3 min). Con la v1 abran http://localhost:3000/ y la consola del navegador (F12 → Console): cliente-api.js imprime una advertencia («API obsoleta: GET /v1/evaluaciones · se retira el … · usa /v2/evaluaciones»). Miren también la pestaña Network: ahí están las tres cabeceras. Ahora cambien en cliente/src/main.js version: 'v1' por 'v2', recarguen y comprueben que todo funciona igual y que la advertencia desapareció. Peguen una captura en ENTREGA.md, sección 5.
¿Qué cambios rompen y cuáles no?

Agregar un campo opcional a una respuesta o un endpoint nuevo no rompe a nadie. Quitar o renombrar un campo, cambiar su tipo, cambiar la forma de la respuesta (arreglo → objeto) o exigir un campo nuevo sí rompe. Clasifiquen ocho cambios posibles en ENTREGA.md, sección 4, y escriban su plan de retiro de la v1.

Listo cuando: npm run test:versionado está en verde (17 pruebas) y el cliente funciona con la v2 sin advertencias. Commit: Parte 4: v2 y obsolescencia de v1.

Parte 5 · Documentar con OpenAPI

15 min

Una API sin documentación solo la puede usar quien la escribió. OpenAPI (la especificación estándar, antes llamada Swagger) describe en un solo documento las rutas, lo que recibe y lo que devuelve cada una, y las herramientas lo convierten en documentación navegable, clientes o pruebas. Su servidor ya lo publica en http://localhost:3000/openapi.json: ábranlo y recórranlo. Está en servidor/openapi.mjs como un objeto de JavaScript.

  1. 5A · Leer lo que ya existe (≈ 3 min). Miren cómo está documentado crearEvaluacion_v1: el cuerpo (requestBody), cada estado de responses con su esquema, la cabecera Location y cómo se reutilizan los esquemas con $ref. Ejecuten npm run test:docs y lean los mensajes: dicen exactamente qué falta.
  2. 5B · La v2 y la obsolescencia (≈ 8 min). Resuelvan los tres TODO del archivo: agreguen 'v2' a las versiones, documenten GET /v2/evaluaciones (parámetros con tipo, límites, valores permitidos y valor por defecto; la cabecera Link; el esquema PaginaDeEvaluaciones que ya existe; el 400) y marquen GET /v1/evaluaciones como deprecated: true con las cabeceras Deprecation, Sunset y Link en su respuesta 200.
  3. 5C · Que no mienta (≈ 4 min). El grupo 5B de npm run test:docs compara el documento con la API real en las dos direcciones: cada ruta del código debe estar documentada, cada operación documentada debe existir, y cada estado HTTP que la API devuelve debe estar declarado. Si la prueba dice «respondió 409 pero la documentación no declara ese estado», una de las dos mintió. Arréglenlo donde corresponda.
Si quieren verla bonita (opcional)

Copien el contenido de /openapi.json y péguenlo en el Swagger Editor (editor.swagger.io): muestra la documentación navegable con las operaciones, los parámetros y los esquemas. Es su API de práctica, sin datos sensibles; con una API real de una empresa, usarían una herramienta instalada en su propio equipo.

Listo cuando: npm run test:docs está en verde. Commit: Parte 5: documentación OpenAPI.

Problemas frecuentes

«node» o «npm» no se reconocen

Falta instalar Node.js (versión LTS) o hay que cerrar y volver a abrir la terminal después de instalarlo. Comprueben con node -v.

Cambié rutas.mjs y el servidor sigue haciendo lo mismo

El servidor carga el código una sola vez al arrancar. Deténganlo con Ctrl + C y vuelvan a ejecutar npm start, o usen npm run dev, que lo reinicia solo al guardar (necesita Node 18.11 o superior). Las pruebas, en cambio, levantan su propio servidor cada vez: no hace falta reiniciar nada para npm test.

La pantalla dice «No existe /v1/evaluaciones» o «El servidor no pudo completar la operación»

Es lo esperado antes de terminar la Parte 2: la API todavía no tiene esa ruta. Si ya la registraron, miren la terminal del servidor: cada solicitud aparece con su estado, y un error inesperado imprime su traza ahí (nunca en el navegador).

El puerto 3000 está ocupado

Elijan otro:

# macOS / Linux
PORT=3001 npm start
# Windows PowerShell
$env:PORT=3001; npm start
# Windows cmd (las comillas evitan que se cuele un espacio al final)
set "PORT=3001" && npm start
En Windows curl no hace lo que dice la guía

En PowerShell, curl es un alias de otro comando. Escriban curl.exe. Y el JSON necesita comillas dobles escapadas: -d "{\"nombre\":\"Parcial 1\",\"peso\":30}". Si les cuesta, usen la extensión REST Client de VS Code o prueben solo los GET con el navegador.

Me aparecen datos viejos de otras pruebas

El servidor guarda en datos/notas.json. Para empezar de cero: detengan el servidor, borren ese archivo y arránquenlo de nuevo. Las pruebas automáticas no lo usan (trabajan en memoria).

Cambié el código del navegador y la página sigue igual

Recarguen con Ctrl + Shift + R y abran la consola (F12 → Console): un error de sintaxis en un módulo detiene toda la app y se ve ahí.

Una prueba espera un estado y mi API devuelve otro

Lean el mensaje: dice qué estado esperaba y cuál llegó. Si discrepan por criterio (por ejemplo, 400 contra 422), vuelvan a la tabla de convenciones de la Parte 2: en el curso las pruebas fijan una convención, y lo importante es que ustedes la puedan justificar.

«Falta documentar…» o «la documentación no declara ese estado»

Abran servidor/openapi.mjs y agreguen la operación o el estado que dice el mensaje (copien la forma de uno que ya exista). Si más bien la API devuelve algo que no debería, arréglenla a ella: la documentación describe lo que quieren prometer.

Las pruebas de arquitectura fallan con «métodos sin implementar»

Todavía queda algún throw new Error('TODO ...') en una pieza. Búsquenlo con Ctrl + F y reemplácenlo por código real.

Git: «rejected» al hacer push

Alguien del equipo subió antes. Hagan git pull, resuelvan los conflictos si los hay, y vuelvan a hacer git push. Para no pisarse, repartan archivos distintos (uno el servidor, otro el cliente).

Plan B: no puedo instalar Node en este computador

Trabajen en pareja con un compañero que sí lo tenga (cada uno puede seguir en su propio repositorio y comparar). O abran el repositorio de su equipo en GitHub Codespaces (botón verde Code → pestaña Codespaces), un editor en el navegador que normalmente ya trae Node.js; tiene una cuota gratuita limitada por mes. Allí ejecutan npm run dev y abren el puerto 3000 desde la ventana de Ports.

Vocabulario

API
El contrato por el que una pieza de software se ofrece a otras: qué se puede pedir, con qué forma y qué se recibe. Una API web va por HTTP.
REST
Un estilo de arquitectura (Roy Fielding, 2000), no un protocolo: cliente-servidor, sin estado, con caché, interfaz uniforme, por capas. «JSON sobre HTTP» no es REST por sí solo.
Recurso
Una «cosa» con nombre que la API expone (una evaluación, el resumen). Se identifica con una URI.
Representación
La forma en que un recurso viaja por el cable (aquí, JSON). No es el objeto interno del Modelo.
Endpoint
Una combinación de método HTTP y URI que ofrece la API (GET /v1/evaluaciones/{id}).
Método seguro
El que no cambia nada en el servidor (GET).
Idempotente
Repetir la solicitud deja el servidor en el mismo estado que hacerla una vez (PUT, DELETE, GET).
Código de estado
El número con que el servidor dice cómo le fue a la solicitud: 2xx éxito, 3xx redirección o «no cambió», 4xx culpa del cliente, 5xx culpa del servidor.
Problem Details
El formato estándar de errores de HTTP (RFC 9457, application/problem+json): type, title, status, detail e instance.
Versionado
Publicar cambios incompatibles bajo una versión nueva (/v2) sin romper a quien usa la anterior.
Obsolescencia (deprecation)
Avisar que algo se dejará de usar (cabecera Deprecation) y cuándo dejará de funcionar (Sunset).
Cambio que rompe
Un cambio que obliga a los clientes existentes a modificarse para seguir funcionando.
OpenAPI
El formato estándar para describir una API REST: rutas, parámetros, cuerpos, respuestas y esquemas.
ETag
Una «huella» de la versión actual de un recurso; sirve para no reenviar lo que no cambió y para no pisar cambios ajenos.
Prueba de arquitectura
Una regla de diseño que una máquina revisa sola (en inglés, fitness function): por ejemplo, «las rutas no tienen reglas de negocio».
